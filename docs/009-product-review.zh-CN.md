## 判断

这个原型适合保留核心调度，围绕首次配置、仓库内工作和结果验收做产品化。当前最明显的断点是：插件已安装并不等于已配置；执行目录存在并不等于有目标代码；会话绑定了工作空间也不等于属于用户正在使用的仓库。

本次完成文档、核心模块、配置前后端、来源接入、执行与恢复路径及相关测试的静态梳理，并对同一基线的源码副本运行 pnpm check：类型检查通过、59 个测试文件 / 1197 项测试通过、构建通过。未启动真实 GitHub / 飞书接单流程，未验证实际 DSH 浏览器画面。界面判断来自组件实现，体验建议仍需真实用户验证。

## 仓库如何工作

它是 DeepSeek Harness 的插件 bundle，不是独立 AI 模型或通用开发 IDE。当前面向一个 GitHub 仓库，可选接入飞书。

GitHub 通知、Issue、PR、评论、CI 或飞书消息进入 Source，形成 Trigger；准入规则与主接单会话决定是否接受；接受后形成 Ticket 和 Assignment；执行器创建该工单的会话和目录；执行结果通过原渠道回传。后续讨论通过订阅回到原工单。

- core：工单生命周期、授权、准入、订阅、派工；Engine 是核心领域对象的统一写入口。
- app：运行时组装、SQLite 持久化、设置、提示词、消息投递、HTTP 管理入口、视图。
- executor：准备工作目录、启动与恢复会话、并发名额及后台任务管理。
- sources：GitHub / 飞书接入，含读取进度、上下文和消息回复。
- client：嵌入 DSH 的 React 管理面板与插件配置入口，已有中英文。
- scripts / SETUP.md：安装、启动、停止、健康检查和由编码助手协助配置的流程。

值得保留的基础包括：持久化工作与重试、重复消息处理、线程后续消息路由、人工问题上报、提示词与配置版本历史、并发控制、失败恢复。不要为新手界面重新实现这些机制。

## 一、首次配置：从分散表单变为可完成的旅程

### 现状与证据

插件管理器仅嵌入 DeploymentPage，主要显示状态目录、机器限制和推导出的账号信息。仓库与账号在 Source，允许接单的人在 Policy，执行目录与 shell 准备命令在 Execution。SETUP.md 依赖编码助手、终端、独立 GitHub 账号、CLI wrapper、DSH profile 和可选的飞书后台配置。

入口分别见 src/client/deployment.tsx、settings.tsx、source.tsx、execution.tsx、src/app/setup.ts 和 SETUP.md。

### 建议的默认旅程

1. 自动检查本机依赖、DSH 模型和已有配置；展示哪些已完成及下一步动作。
2. 选择当前仓库，自动识别本地路径、远端与默认分支；核对远端与监听仓库一致。
3. 连接执行账号，清楚展示“谁会发表评论、提交代码”，提供登录入口和权限检查。
4. 确定谁能交给它工作；默认只允许自己，GitHub 先行，飞书按需展开。
5. 选择工作方式：当前仓库串行执行，或独立分支并行执行；用户不必编写 shell。
6. 运行不发消息、不推送的自检，展示仓库、工作目录、账号和模型；另设明确的端到端试单动作。

配置结束应有可核对的摘要，而不是只显示“保存成功”。失败文案写“哪里没连上、影响什么、点哪里修复”。高级限制与原始命令默认折叠。

### 边界

插件内向导只能改善安装后的配置。要实现从零开始完全图形化，还需要处理 DSH / Node 等前置安装、模型配置、服务启动及失败时的诊断入口。插件未启动时，不能依赖插件自身页面修复启动问题。

GitHub 独立账号与飞书应用的创建、授权仍需用户完成外部操作；向导可引导并检查结果，不能承诺自动完成所有外部步骤。秘密不进入聊天记录，优先沿用 CLI 凭据存储。

复用现有设置块、结构化 SetupProblem 和修订号；向导是这些配置的统一入口，不另建一套配置数据库。跨设置块保存失败时保留进度，继续或回退，不显示错误的“全部完成”。

验收：首次接触的用户无需手写 YAML / shell，即可完成插件安装后的配置；刷新保留进度；每个失败都有修复入口；最后可证明会话绑定了正确的本地仓库。

## 二、接单会话：显式绑定当前仓库

### 已确认事实

- src/app/sessions.ts:138 的 ensure 会调用 workspaceRegistry.create(cwd)，并把 workspaceId 传给会话创建接口，因此并非完全没有工作空间。
- 对应 DSH 依赖会按规范化后的目录复用工作空间；同目录无需重复创建。
- src/app/runtime.ts:210 把主接单会话建在 stateDir。
- src/executor/dsh.ts 的 ticketExecution 始终将执行目录设为 executionRoot 下的工单短名子目录。
- executor.prepare 默认空字符串；不填命令时创建空目录，不会自动检出目标仓库。
- 工单会话具有稳定身份，重试和恢复会复用；它们不应简单理解为一次性临时会话。

因此，只把“执行目录”填写为当前仓库，现有逻辑仍会在其下创建工单子目录，不能达到直接在仓库根目录工作的目的。

### 最小可行设计

在现有 executor 设置中加入本地仓库路径和工作方式，不新建一套项目 / 任务 / 会话领域模型。

| 方式 | 实际行为 | 适用场景 |
| --- | --- | --- |
| 当前仓库 | 每个工单保留独立会话，同一真实仓库目录复用 DSH 工作空间 | 当前用户最需要的、可直接看到并接续修改的开发方式 |
| 独立分支 | 从该仓库建立每个工单的 git worktree，自动处理分支与目录 | 多任务并行、需要隔离修改的场景 |

第一版建议先交付当前仓库模式：会话在当前仓库根目录执行；主接单会话也绑定该仓库；数据库仍留在 stateDir。当前仓库模式必须按仓库限制同时修改的工单为一个，继续利用现有调度队列，避免多个会话切换同一工作区的分支与覆盖文件。此锁不能阻止用户自己或其他进程编辑，界面需检测已有改动并明确处理方式。

自动接单前检测未提交修改、正在进行的 merge / rebase、远端与监听仓库不一致。遇到已有修改时保留现场并提示，不自动 stash、reset 或覆盖。将工作方式固化到工单执行信息，设置变动不偷偷迁移正在运行的工单。

会话标题显示工单与来源；工单页展示仓库、分支、真实目录和会话入口；后续评论、重试及重启继续回到原会话。

### 产品边界：同一目录与同一 DSH 界面是两件事

官方部署建议单独的 superagent profile，原因是插件会修改进程级 PATH 和 Git 环境，且需要独立重启。复用仓库路径，只会在当前插件所在的 DSH 环境里建立该路径的工作空间，不能据此保证会话出现在另一个个人 profile 的侧栏。

第一版可以保留独立服务，提供“打开这个仓库的执行会话”入口；如果必须直接出现在日常使用的 DSH 界面，应先把 worker 的环境改为子进程级，再评估同 profile 运行。跨 profile 会话桥接会增加结构，暂不建议引入。

### 后续并行模式

worktree 让不同工单不互相污染，但在现有 DSH 模型中，工作空间身份按路径确定，不同 worktree 自然是不同工作空间。若还要把这些会话统一显示在一个仓库下，需要确认 DSH 是否支持仓库分组，或修改宿主的展示能力，不能仅更改插件的 workspaceId。

相关回归重点：相同仓库复用工作空间；多个工单串行；后台任务仍持有修改名额；追问回原会话；停止 / 重试 / 重启；已有改动不丢失；旧工单仍沿用旧目录；接管 PR 的分支关联规则不被破坏。

## 三、其他值得完善的点

| 优先级 | 完善项 | 价值与范围 |
| --- | --- | --- |
| P0 | 工作目录就绪检查 | 目录存在不能代表准备成功。当前准备失败可能留下非空目录，后续又把存在视为已准备；启动前需验证目标 Git 仓库、预期分支与准备结果 |
| P0 | 暂停语义清晰 | 现有“暂停处理”停止新调度和投递，不中断正在运行的执行器。按钮旁说明实际影响，并与停止某个工单区分 |
| P0 | 权限说明与关键动作策略 | 当前执行会话以操作者身份全权限运行，命令 wrapper 不是安全隔离。图形化展示可访问范围；若要求推送、合并等操作必须确认，要通过可执行策略实现，不能只改提示词 |
| P1 | 面向验收的结果卡 | 汇总改了什么、验证结果、未完成项、分支 / PR / diff；沿用工单与报告，减少跳转日志查找结果 |
| P1 | 成本与失控保护 | 已有并发与模型预算重试状态；补充按工单展示用量、运行时长及部署预算阈值。精确费用依赖提供方计量，不伪造估算 |
| P1 | 统一故障修复 | 把 setup、来源读取、模型限流、投递失败映射为用户动作；先判断故障再提供重试，避免无意义重启 |
| P1 | 会话与目录整理 | 完成工单默认折叠 / 归档。清理 worktree 前确认无未提交修改、无仍需保留结果且后台已结束；不默认删除会话历史 |
| P2 | 兼容性与升级 | 明确支持的 DSH 版本、升级前配置备份与回退方式；目前依赖 alpha 系列 API，应在升级时验证关键会话流程 |
| P2 | 多仓库 | 目前产品假设是一仓库一部署。先把单仓库闭环做好，再决定是否需要多仓库；当前不引入平台级组织体系 |

## 推荐顺序

1. 打通当前仓库路径选择、工作空间复用、串行执行和目录就绪检查。
2. 在现有配置之上实现统一向导，先覆盖 GitHub；插件入口与主面板进入同一旅程。
3. 补齐结果卡、故障修复和会话归档，完成试单到验收闭环。
4. 再增加自动 worktree、飞书向导与预算控制。

这个顺序优先保证“在正确的仓库可靠地完成一件事”，再降低配置成本，最后扩展并行规模。无需先重写 Engine，也无需增加新的项目管理系统。
