# DSH Superagent 个人开发者版开发规格

本文用于启动实现。设计基线为 `feat/multi-repository` 的 `aa78913`，开工时以工作区当前源码为准，并保留已有改动。本文更新了[多仓库施工方案](010-multi-repository-construction-plan.zh-CN.md)中关于 worktree、并发和执行 Agent 的首版范围。

## 1. 首版交付目标

用户在一个入口添加 GitHub 仓库、连接飞书群并选择本机执行 Agent。群里发来的需求进入绑定仓库。互不冲突的任务在独立 worktree 并行，Worker 把实现交给本机 Codex、Claude Code 或现有 DSH 执行方式。代码通过 GitHub PR 交付，结果回到原话题。

| 必须交付 | 用户能观察到的结果 |
| --- | --- |
| 不同飞书群绑定不同仓库 | A 群任务只进入仓库 A，B 群任务只进入仓库 B，历史追问沿用原话题归属 |
| 多 worktree 并行 | 跨仓库可并行，同仓库范围互不重叠的工单也可并行。发生重叠时能看到等待原因 |
| GitHub 继续作为交付中枢 | 新需求产生对应 PR，已有 PR 的任务沿用既有归属。CI、审阅、合并、关闭继续以 GitHub 为准 |
| Worker 能指挥本机 Agent | Worker 可在同一张工单中委派、接收结果、继续或停止 Codex 和 Claude Code，二者都能承担实际代码实现 |

首版面向信任仓库的本地单操作者。每张工单归属一个仓库，多仓库能力体现为多条独立任务同时进行。新增执行能力沿用 Ticket、Assignment、Runtime、Engine 和现有 SQLite 持久化。管理器负责路由和容量，仓库实例负责接单、执行和交付。

## 2. 飞书路由与仓库实例

### 2.1 绑定和投递

1. 一个群绑定一个仓库，一个仓库可绑定多个群。群的稳定标识用于路由，群名用于展示。消息正文中的仓库名或路径属于任务上下文。
2. 新话题按当时生效的群绑定路由。已有话题沿用持久化的仓库归属。群换绑前显示未完成任务和积压，先处理该群的在途工作，再将新话题指向新仓库。
3. 入站事件先持久化目标，再投递到该仓库实例。实例接收记录落库后才确认。以现有稳定 Trigger ID 消重，覆盖投递成功但确认丢失的情况。
4. 投递保持同一话题的已知事件顺序。一个话题退避重试，或一个群停用时，其他可投递话题继续推进。可以沿用现有管理队列调整调度粒度，撤销按仓库单一队首阻塞的行为。
5. 群停用时暂停该群的接入和发送，保留已持久化的待处理记录。恢复前重校验群、话题和原仓库。回复经现有渠道检查目标归属并去重，GitHub 交付状态和群消息送达状态分别记录。
6. 绑定决定仓库归属。仓库 Policy 继续决定谁可以开启或继续工作。托管绑定和名单由管理入口维护，仓库实例展示其生效值，避免同一字段从两个入口写入后被覆盖。

### 2.2 实例就绪与恢复

仓库可以在未连接飞书时启动并通过 GitHub 工作。分别展示实例在线、仓库可执行、执行 Agent 可用、飞书连接和待投递量。设置有缺项时保留可访问的修复入口。仓库离线时，已接收消息保留原目标。管理器重启后重新发现仓库实例，恢复投递和容量视图。

入口见 [管理器运行时](../src/manager/runtime.ts)、[路由和队列](../src/manager/store.ts)、[实例启动](../src/manager/instances.ts)和[实例接收接口](../src/app/http.ts)。

## 3. Worktree 与并发

### 3.1 工作区生命周期

- 托管仓库的新任务默认使用 `worktree`。安装或接入时校验本地仓库与 GitHub 远端，准备产品管理的 Git 工作区。每张新工单的执行记录保存仓库身份、目标/来源分支、基准提交 SHA、任务分支和 worktree 路径。产品在启动前创建并验证，Agent 使用分配好的目录。
- 新 PR 任务以目标分支的已知远端提交为基准，任务分支采用现有可识别的工单分支命名。已有 PR 任务先核对来源仓库、head、base 与写权限。有权限时沿用获授权的 PR 分支，否则明确阻塞并保留调查结果。
- 目录准备需要能在中断后续接。核对 Git 的 worktree 登记、预期分支、仓库归属和已记录的准备状态。目录存在、分支创建成功、工作区就绪是三个不同事实。重试沿用可验证的现场，发现不匹配或人工改动时保留现场并提示处理。
- 原工作目录始终保留用户未提交的改动。旧 `current` 工单继续在原目录串行执行，旧 `isolated` 工单沿用既有准备方式。开启新模式只影响后续工单。同一仓库已有 `current` 工单处于执行、停止中或待确认恢复时，新模式的写入等交接完成。
- 归档和清理复用工单状态。只有在后台工作已停止、没有待保留的本地改动且远端交付状态已核对后，才允许清理。清理前保留可供后续追问使用的仓库、分支、提交和 PR 关联。

Git worktree 共享部分仓库配置、引用和对象。由仓库实例管理共享 Git 元数据的写入，使用任务目录隔离修改，并对产品管理的目录与分支做所有权校验。 [Git worktree 文档](https://git-scm.com/docs/git-worktree)

### 3.2 调度规则

| 条件 | 行为 |
| --- | --- |
| 不同仓库 | 独立执行，受机器总容量约束。已声明的共用测试数据库、端口等资源出现重叠时排队 |
| 同仓库，已知写入范围不重叠 | 在独立 worktree 并行。仓库实例在启动写入前记录范围占用 |
| 同仓库，写入范围重叠 | 等待持有该范围的工单，任务页展示阻塞来源 |
| 写入范围未知 | 先只读调查。确认范围后进入并行判断，仍无法圈定范围时使用整个仓库的写入名额 |
| 执行中发现需要扩大范围 | 先暂停超出范围的写入并申请扩展。已产生的超范围差异保留在隔离工作区，确认允许前不得进入 GitHub |

首版按仓库内文件、目录及声明的共享资源判断。目录覆盖下级文件，同一文件的不同代码段按重叠处理。路径按实际工作区规范化，考虑大小写、别名、符号链接和目录边界。一个 worktree 只有一个写入者，适用于 Worker、外部 Agent 和人工接续。不同 worktree 的同仓库修改在发布前还需核对实际 diff、相关开放 PR 的改动和最新目标分支。接口或行为层面的冲突通过相关测试、CI 与人工审阅把关。

沿用 Executor 的启动及恢复入口。管理器管理整机执行容量，仓库实例管理仓库内范围与名额。正在启动、恢复、执行和停止中的作业均计入容量。停止后确认写入者和其后台工作已结束再释放名额。等待人工审阅的工单可以释放运行名额，未合并 PR 的实际改动仍参与交付前检查。重启后先核对在途作业，随后发放新名额。

入口见 [执行元数据](../src/core/model.ts)、[工单执行器](../src/executor/dsh.ts)、[Git 仓库校验](../src/infra/repository.ts)、[设置保存](../src/app/settings.ts)和[派工恢复](../src/core/assignments.ts)。

## 4. Worker 委派本地 Agent

### 4.1 调用约定

Worker 直接调用受工单约束的委派工具。仓库保存默认执行 Agent，单个任务可明确选择其他已接通的 Agent。保持现有 DSH 执行选项，Codex 和 Claude Code 使用同一套委派、状态、续接及停止语义。

| 方向 | 最小信息 |
| --- | --- |
| Worker → Agent | 实现目标、相关上下文、允许的写入范围、验收条件、只读或写入权限、时限 |
| 宿主补充 | 从当前工单推导仓库、Assignment、工作目录和基准提交，从已验证的本机配置选择命令与权限 |
| Agent → Worker | 运行结果、会话标识、改动摘要、检查记录、阻塞原因和可用的用量数据 |

由宿主限制可选的 Agent 及参数，按当前工单运行。Codex 和 Claude Code 的非交互调用、事件解析、会话续接差异留在各自适配中。结构化完成事件、进程退出、目录实际差异和验证结果分开记录，退出码成功只表示进程成功退出。Worker 在确认结果前读取真实差异和所需检查证据。 [Claude Code 非交互接口](https://code.claude.com/docs/en/headless)

### 4.2 作业、取消和恢复

外部运行归属既有 Assignment。每次调用保存运行 ID、执行者、外部会话标识（如有）、工单目录、状态、时间和必要结果。重复提交相同调用只返回已有运行。Worker 等待期间可结束当前回合，运行完成后用现有后台结果交付方式唤醒原 Worker。旧 Assignment 的迟到结果仅作记录。

停止工单同时收束该工单的 Agent 及其后台进程。收束未确认时保留写入名额，并显示“正在停止”或具体异常。重启后，先核对运行状态与工作区变更，外部会话可用时续接，无法续接时在保留现场的前提下让 Worker 决定是否重试。登录过期、额度不足、权限不足和执行超时分别报告。切换执行者需用户明确选择，前一个写入者先完成交接。

### 4.3 权限与数据

外部 Agent 使用自己的模型连接和工单工作区。启动时校验实际权限边界，约束文件访问、子进程和所需网络，凭据与配置按执行方式单独提供。工作目录或提示词只能表达约定，权限限制需要由可执行的运行策略承担。宿主应能验证外部 Agent 无法使用交付账号、飞书机器人、其他仓库目录或实例管理凭据。无法建立所需约束时，显示该执行方式不可用。

Worker 只传任务所需上下文，飞书私有聊天、附件和凭据不得随运行环境或完整历史一起转交。设置页说明本机执行进程使用哪个模型提供方，代码与上下文可能发送给谁。可用用量按提供方真实数据展示。

入口见 [Worker 工具](../src/app/tools/executor.ts)、[会话与工具注册](../src/app/sessions.ts)、[后台任务控制](../src/executor/background.ts)和[执行生命周期](003-execution.md)。

## 5. GitHub 交付契约

1. Worker 核对授权范围、实际 diff、基准和验证结果后，通过仓库既有 GitHub 身份提交及推送。PR 归属仍由现有代码检查，创建于工单分支的 PR 和来自原请求的 PR 都沿用既有规则。对现有 PR 的更新需要核对远端最新 head，发现他人更新或冲突时阻塞并展示原因。
2. 推送和创建 PR 前记录计划目标及提交。结果未知时查询该仓库的分支、提交 SHA 和 PR 归属，先恢复已生效操作，再补做缺失步骤。重复执行同一交付动作应获得同一结果，避免创建第二个 PR 或覆盖他人提交。
3. CI、审阅、合并、关闭继续由 GitHub Source 回流原工单。审批、合并及自动合并沿用仓库既有策略与保护规则。外部执行 Agent 负责实现和验证，GitHub 交付动作始终由原 Worker 发起并经宿主执行。
4. 用户看到代码已准备、PR 待审阅、合并/关闭、原渠道送达几类事实。做到可审阅时回原话题发送结果与 PR 链接，最终 PR 状态按现有规则通知。GitHub 已完成、飞书消息待送达时，任务页分别显示两项状态。

入口见 [PR 关联和回流](../src/sources/github-pull.ts)、[Worker 报告](../src/app/tools/executor.ts)、[交付要求](../prompts/team/delivery.md)和[出站队列](../src/app/outbox.ts)。

## 6. C 端使用路径

部署入口提供当前支持平台的安装与就绪检查。进入面板后，用户在同一流程选择本地仓库、识别 GitHub 远端、连接交付账号、选择本机 Agent，然后按需绑定飞书群和发起试单。采用系统可用的目录选择或现有工作空间列表。初次检查验证通路和权限，发第一条群消息或创建 PR 由明确的试单动作触发。

统一任务列表显示仓库、原话题、Agent、当前阶段、等待原因和 PR。用户能直接进入对应工单处理阻塞、停止、重试或打开 GitHub 审阅。运行详情提供 worktree、基准提交、实际改动概要、检查证据和 Agent 会话。原有 DSH 会话与诊断仍可从任务详情进入。

默认给用户展示少量可操作的选择。命令路径、运行日志、策略历史和实例诊断放在对应设置或详情。保存设置时说明现在是否生效、影响新工单还是在途工单。管理列表以仓库 ID 与工单 ID 定位，通过已鉴权的实例接口读取现有状态。

## 7. 实施顺序与各阶段退出条件

先阅读 [领域模型](001-domain.md)、[授权语义](002-authorization.md)、[执行说明](003-execution.md)和[现有多仓库行为](multi-repository.md)。检查工作区状态、`package.json` 支持的 DSH 版本以及现有命令入口。保留在途改动，优先复用已有设置、后台任务、队列和 GitHub 流程。按下面顺序做可分别审阅的提交。

| 阶段 | 实现入口与工作 | 退出条件 |
| --- | --- | --- |
| A · 固定路由与就绪 | `src/manager/{store,runtime,instances}.ts`、`src/app/http.ts`。固化绑定、去重和话题投递顺序，拆开仓库就绪与飞书就绪 | 两群两仓无串路。无飞书也能启动并通过 GitHub 工作。群停用后其他群队列继续，离线恢复后仍投原仓 |
| B · 托管 worktree | `src/executor/dsh.ts`、`src/infra/repository.ts`、`src/core/model.ts`、现有设置与迁移。加入工作区准备、恢复、范围占用及配额 | 真实临时 Git 仓库中可验证两工单并行、同文件排队、准备中断后复用、旧模式兼容及用户目录保留 |
| C · 本地 Agent | `src/app/tools/executor.ts`、`src/app/sessions.ts`、`src/executor/background.ts`及适配代码。先用可控进程验证委派生命周期，再接 Codex、Claude Code | Worker 能委派、收结果、续接和停止两种 Agent。旧运行的结果不能改动当前工单，先收束再释放写入名额 |
| D · GitHub 交付和面板 | `src/sources/github-pull.ts`、`src/app/outbox.ts`、`src/client/manager.tsx`和工单视图。核对 PR 对账，打通日常任务与首次使用 | 用户通过统一入口完成配置、发起、查看与验收。两种 Agent 的结果都走原 GitHub PR 链路并回原话题 |
| E · 兼容和发布验收 | 测试、升级说明和真实双仓联调。对已有部署保留工单与待投递记录，使用测试仓库和测试群验证发布 | 通过下面的验收矩阵，`pnpm check` 通过，交付记录包含真实联调证据和剩余限制 |

## 8. 验收矩阵

| 场景 | 通过标准 |
| --- | --- |
| 两群两仓同时发单 | A、B 群的任务进入正确仓库，两个仓库有重叠的执行时间，PR 在各自仓库，回执只到各自原话题 |
| 重复、停用、离线与换绑 | 重复事件只产生一次有效接单，同话题保持顺序，停用群或仓库离线不阻塞无关任务，换绑后旧话题仍能续接原仓 |
| 同仓库两个独立改动 | 在不同 worktree 同时运行，两个分支和 PR 可独立审查，用户原工作区的未提交改动保持原状 |
| 范围重叠与扩大 | 同文件任务在写入前等待，未知范围先只读，实际超范围差异和发生冲突的远端更新进入人工处理 |
| Codex 与 Claude Code | 两种 Agent 分别实际完成代码改动，Worker 验证并通过 GitHub 推送和发 PR。使用其中一种实现、另一种只读审阅可在同一工单完成 |
| 能力、权限和上下文 | 未安装、未登录、权限不足时给出对应修复信息。外部 Agent 无法访问其他工单目录或交付凭据。发布内容可追溯到指定 worktree 和已验证提交 |
| 停止、崩溃、恢复 | 外部进程及子进程收束后才释放名额，保留本地现场。模拟 worktree 准备中断、Agent 运行中断、GitHub 成功后回执丢失、飞书发送失败，恢复后无重复写入、PR 或回执 |
| 旧部署和首次使用 | 旧工单保持原路径和 PR，升级可保留历史和积压。新用户能根据页面完成仓库、Agent、GitHub 与群绑定配置并独立发起试单 |

自动化优先复用现有 `repository`、`manager-*`、`runtime-concurrency`、`background`、`migration`、GitHub 和面板测试。真实验收使用两个独立测试仓库和两个已获授权的飞书测试群，保存工单与 PR 链接、重叠运行时间、冲突等待和恢复证据。测试替身、CLI 帮助和进程退出码只能验证对应层次，真实外部交付以 GitHub 和原飞书话题中的结果为准。

升级先备份管理库、仓库状态和 DSH 会话，停止共享同一机器人事件流的旧消费者后再切换。若需回退，保留已确认接收的事件、未送达回执和已创建的 GitHub PR，并明确如何重放和重新关联。旧数据仍应由原工单语义读取。
