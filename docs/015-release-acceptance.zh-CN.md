# 企业交付验收与发布记录

本文件用于决定一个版本是否可以交付客户。页面能打开、构建成功、自动化测试通过，分别证明不同的事项。客户生产环境的验收需保留实际运行证据。

本轮源代码版本为 `0.1.1`，最终交付物还必须以发行包 SHA-256 区分具体构建。

## 交付范围

当前产品形态是客户独立部署的研发协作工作台。一个 DSH 管理服务连接多个团队的仓库，开发者通过授权的 GitHub 或飞书身份提交需求，运维人员使用统一面板管理接入与运行。每个客户使用独立部署目录、服务身份和凭据。

单客户环境内，各团队处于同一已批准的操作系统信任域。仓库服务有独立状态、工作目录和授权配置；它们使用同一个操作系统服务身份。这不构成敌对租户之间的操作系统隔离。当前版本不提供公网多租户 SaaS、企业 SSO、按用户分级的管理角色或计费系统。

产品线、团队数与开发者名单来自客户实际登记。代码中的 5 团队、12 产品线、120 人样例是输入校验和容量规划用例，不能作为真实部署、压测或效率达标证据。

## 客户上线步骤

1. 按 `ops/enterprise/README.md` 准备专用非管理员服务身份、DSH `0.2.2-rc.5`、Node.js `24.9.0` 或更新版本、GitHub 访问、模型额度和可选飞书机器人。宿主 Node.js 下限依据 [官方 CLI 的版本声明](https://github.com/deepseek-ai/deepseek-harness/blob/dsh-v0.2.2-rc.5/apps/cli/package.json)，不能以插件自身的 Node.js 兼容范围替代。
2. 安装并确认管理服务只监听本机。远程运维通过受控 SSH 转发进入，使用专用运维凭据解锁。
3. 在统一面板添加真实仓库，填写团队、产品线与接单身份。保存成功仅表示登记和相应检查完成。
4. 飞书场景先验证机器人，再把已授权的研发群绑定到仓库。核对成员授权和目标仓库，不用测试消息代替真实成员授权。
5. 先启动一个目标仓库，检查分支保护、模型和执行工具状态。仓库设置或模型不满足条件时，记录阻断原因并修正。
6. 用客户指定的测试需求走完整闭环。未授权用户不得发起或追问执行，执行结果以草稿 PR 交付，人工审批和 CI 仍由客户代码流程执行。
7. 再逐步启用其余仓库，观察排队、模型限额、CPU/内存/磁盘、错误与恢复情况。

登记数量、正在运行数量、群聊数量和已授权身份数量应分别验收。GitHub 身份数与飞书身份数不能直接相加为唯一员工人数。

## 备份和恢复

状态包含管理数据库、仓库数据库、会话、持久队列、工作目录、DSH profile 及凭据。只复制单个 SQLite 文件不足以恢复整个部署。运行中的 SQLite 数据库可能含 WAL 文件；备份必须使用一致性快照或完成停机后复制完整目录。

以下是同一主机、同一服务身份、同一绝对部署路径的停机备份流程。执行前确认部署路径。如果由 systemd 托管，先停止 supervisor，避免它在维护期间拉起服务。备份包含凭据，应按与原部署相同的保密级别保管。

```bash
umask 077
DSH_DEPLOY_ROOT="$HOME/dsh-enterprise"
DSH_BACKUP_ROOT="$HOME/dsh-backups"
mkdir -p "$DSH_BACKUP_ROOT"
"$DSH_DEPLOY_ROOT/dsh-enterprise" stop
DSH_SNAPSHOT_PATH="$DSH_BACKUP_ROOT/dsh-enterprise-$(date +%Y%m%d-%H%M%S)"
"$DSH_DEPLOY_ROOT/dsh-enterprise" backup "$DSH_SNAPSHOT_PATH"
"$DSH_DEPLOY_ROOT/dsh-enterprise" verify-backup "$DSH_SNAPSHOT_PATH"
```

`stop` 返回失败时不继续备份；先处理未停止的仓库或管理器。服务进程停止后再执行复制，不能另起第二套飞书消费者代替停机。

工具在维护前检查管理器 PID、仓库端口与状态锁。快照保留完整部署数据，逐文件校验 SHA-256，并验证私有文件权限；符号链接只保存链接本身，不复制它指向的外部内容。外部 DSH、工具、SSH 和系统钥匙串仍由主机恢复方案保障。

恢复只支持原路径、同 profile、相同 release SHA-256。确认没有运行中的管理器或仓库后，执行 `dsh-enterprise restore "$DSH_SNAPSHOT_PATH"`。工具先自动生成恢复前完整副本，再复制和验证待恢复目录；恢复后保持停机。`service.json`、DSH profile 和仓库状态含绝对路径，不能把备份随意移到新目录后直接运行。先对账，再启动管理器并核对列表，最后逐个启动仓库。

恢复旧快照会丢失快照后的已接收事件与设置。必须核对恢复点和停机区间，不能把恢复备份描述成无损回滚。

## 升级与回滚要求

现有安装器要求新目录，不是原地升级工具。版本发布应保留已发布包及其 SHA-256，不覆盖旧包。升级流程需先收束新任务、停止服务、做一致备份，再验证目标版本的数据兼容性与插件加载。

不能重新运行 `--from-default-profile` 覆盖已有 profile；这会替换原配置。已初始化仓库在启动前会检查实际插件路径；路径变化时通过官方离线插件命令重连当前包，并核验链接结果。更新状态以原子文件记录，失败可重试。该分支不重写配置文件或打开业务数据库。13 项实例回归已通过，覆盖路径变更、路径别名、失败重试和配置/工单保留；尚未在客户主机完成真实版本升级演练。

数据库迁移没有经过逆向兼容验证时，不得让旧程序直接打开已升级的状态。回滚以经过演练的完整一致性备份为准，并明确恢复点之后的业务对账。发布新版本前，把升级和恢复命令加入发行包并在干净环境演练；尚未验证的流程不得标为已支持。

## 运维责任

| 项目 | 要求 |
| --- | --- |
| 健康检查 | 管理器认证检查、仓库在线/就绪状态、模型可用性分别观察 |
| 磁盘 | 监控数据库、工作目录和日志增长；`rotate-logs` 在停机后轮转达到 20 MiB 的日志并保留五代，当前没有在线自动轮转 |
| 凭据 | 服务身份持有；备份与日志访问限于指定运维；换凭据后重新验证连接 |
| 撤权 | 停止新调度，核对运行任务，再更新名单并验证未授权拒绝 |
| 故障 | 保留失败原因和事件标识，确认队列后再重试；不将消息转投给其他仓库 |
| 支持 | 每个客户交付前指定产品维护方、技术支持联系人、响应范围及版本维护周期 |
