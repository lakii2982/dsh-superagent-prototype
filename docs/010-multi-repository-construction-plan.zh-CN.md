# 多仓库与飞书群绑定施工方案

状态：设计方案，尚未实施产品代码。
日期：2026-11-17。
基线：8c32a9dc5d72c033816c6a8110b37f40cf94fba4。

## 1. 交付目标

一个插件入口、一套飞书机器人，管理多个仓库。每个群绑定一个仓库，一个仓库可绑定多个群。群内需求自动进入对应仓库；工单会话在该仓库的真实工作目录执行，后续消息继续进入原工单。

首版保留现有单仓库 Engine，通过独立运行实例隔离仓库。增加轻量管理入口与飞书分发层，不新增另一套任务系统，不依赖模型判断目标仓库。

首版不做跨仓库自动拆单、跨仓库统一长会话、自动合并、多租户管理。私聊和未绑定群不启动开发任务。现有单仓库部署保留原有行为，进入新模式时才应用新默认值。

## 2. 总体结构与职责

统一管理入口
→ 仓库配置、群聊绑定、运行状态、跨仓库任务摘要
→ 飞书接入：单一事件消费者、历史补收、持久化分发、集中发送回复
→ 仓库 A 的独立 DSH profile / 进程 / 状态目录 / Engine
→ 仓库 B 的独立 DSH profile / 进程 / 状态目录 / Engine

管理入口和接入层可放在同一进程，第一版不拆微服务。仓库实例继续复用现有 Runtime、Engine、Executor 与 SQLite。每个实例的端口由管理层分配，不让用户管理。

职责约束：

- 接入层只决定消息属于哪个仓库并可靠投递；不评估需求、不创建工单。
- 仓库实例继续判断接单权限、范围和后续消息归属，复用现有 Engine。
- 飞书事件流和群历史补收由接入层统一管理；实例不再启动各自的飞书事件消费者。
- 已订阅话题的补读仍可复用现有逻辑，但读请求经受控接入适配器完成，不能重复触发另一条独立接单路径。
- 统一面板聚合各实例的视图，不直接修改各实例数据库。
- 实例离线不改变消息目标，其他仓库继续工作。

独立进程解决环境污染与故障传播，不构成文件或凭据的安全隔离。首版仅面向同一操作者信任的本地仓库；强隔离是后续独立能力。

## 3. 必需配置与持久化记录

以下为逻辑字段，最终沿用仓库现有 Zod schema 和设置修订机制，避免自建配置框架。

### 仓库配置

- id：稳定内部标识，仓库改名不变。
- name：显示名称。
- remote：GitHub owner/name。
- directory：真实本地仓库路径，规范化并验证 Git 根目录。
- executionMode：current 或 worktree；首版仅开放 current。
- enabled：是否接收新工作。
- 实例的 profile、stateDir 和本地连接信息由管理层生成。

同一个规范化工作目录不允许注册两次。GitHub 仓库重命名允许更新 remote；将现有记录替换成另一个实际仓库时应新建记录，避免旧任务串仓。

### 群聊绑定

- botId + chatId：绑定唯一键；首版仅一套机器人，但明确记录身份。
- repositoryId：仓库归属。
- listen：默认 mentions；已有工单话题的追问按既有规则接续。
- enabled：是否接收新需求。
- revision、effectiveAt：绑定修订与生效时间。

群名作为可刷新展示信息，不参与路由。一个群只允许一个当前有效绑定，唯一性由存储约束保证，不能只靠表单检查。

接单白名单与群成员同步复用仓库实例现有 Policy；不能因为绑定了群就自动允许所有群成员发起工作。

### 路由记录

- 每条入站消息：机器人身份、消息 ID、目标仓库、绑定修订、接收时间、投递状态和错误。
- 每个话题：原始话题标识、固定仓库归属、建立时间。
- 每条待发回复：仓库、目标群 / 话题、现有 OutboundMessage ID、发送结果。

这是必要的可靠投递记录，不引入新的业务工单或派工概念。实例数据库内部 ID 可以保留；聚合视图、跨进程请求与链接统一使用 repositoryId + 原 ID，避免冲突。

## 4. 路由规则

1. 校验消息来自已配置机器人接入，不接受正文指定的 repositoryId 或本地路径。
2. 如果话题已有固定仓库归属，优先使用原归属；后续追问不跟随群的新绑定漂移。
3. 否则按 botId + chatId 查找有效绑定。
4. 新话题只接收绑定生效后的新需求；历史补收仅恢复启用后遗漏的消息，避免首次接入立即执行旧需求。
5. 通过持久化事务同时固定消息目标与必要的话题归属，再进行异步投递。
6. 仓库实例先验证来源绑定，再执行现有准入、订阅和接单逻辑。
7. 成功持久化接收后返回确认；接入层收到确认才标记投递完成。

同一消息在“已交给实例但确认丢失”时可能重投，采用至少一次投递；复用确定性 Trigger ID 和现有幂等机制，保证只接单一次。不能宣称跨两个数据库天然 exactly-once。

同一话题按持久化接收顺序投递，补读消息使用来源时间及 ID 做稳定排序；不保证网络乱序消息能恢复绝对原始顺序。后续追问应等待已知父消息完成入库；异常放入可诊断的重试状态，不能换仓库绕过错误。

未绑定群不执行、不逐条回复。机器人私聊暂不接单，避免没有仓库归属的需求；管理面板提供试单入口。

### 绑定变更与停用

- 有开放工单的群，首版禁止直接换绑，先完成或停止旧工单。
- 换绑只改变新话题归属；旧话题包含已结束工单，继续固定在原仓库，以保留恢复语义。
- 换绑前展示这一影响；用户希望在新仓库执行时，应发起新话题。
- 暂停新需求、暂停处理、停止某个工单分别展示，不复用同一个含糊开关。
- 紧急禁用群时，接入层停止该群的自动投递和回复，待发消息保留。恢复后再次验证权限与目标。
- 仓库离线时保留队列并显示积压，不把消息交给其他实例。
- 有历史关联的仓库使用归档而非直接删除，保留追溯入口。

## 5. 当前仓库执行

为 existing executor 设置增加明确的本地仓库路径和执行模式。

current 模式：

- ticketExecution 使用仓库根目录，不再自动追加工单短名。
- 工单仍拥有独立且持久的执行会话；DSH 根据同一路径复用工作空间。
- 主接单会话绑定该仓库，状态数据库继续保存在独立 stateDir。
- 工单建立时固定目录和执行模式，后续设置变化不迁移正在执行的工单。
- 同目录只允许一个执行工单占用修改名额，后台工作同样占用名额。
- 开始前核对远端、分支和 Git 状态；已有用户修改、merge / rebase 等情况应保留现场并提出处理要求，不自动 reset 或 stash。
- 同一个本地仓库只能交给一个受管理实例，防止实例之间并行写同一目录。
- 用户手动编辑及外部程序不受内部调度锁约束，交接前后再次检查目录变化。

会话出现在对应仓库实例的 DSH 工作空间，统一面板提供直接打开入口。首版不承诺这些会话自动出现在另一个个人 DSH profile 的侧栏；跨 profile 同屏展示属于宿主集成后续工作。

worktree 模式后续交付，必须同时覆盖分支关联、失败准备重试、PR 接管、恢复和安全清理，不能只自动拼接 prepare 命令。

## 6. 进程边界与接口

沿用本地 HTTP 和现有资源视图；新增实例间入口与浏览器管理入口区分。

- 实例间接口仅监听回环地址，使用每实例独立的随机凭据；凭据存于受限文件，不进入面板响应、URL 或日志。
- 浏览器操作沿用现有同源校验和修订号，不把内部凭据发给前端。
- 接收接口拒绝目标仓库与实例不一致的请求，并限制大小、校验数据结构。
- 回复通过接入层发送；校验回复的仓库和话题所有权，不能只信任实例提交的任意 chatId。
- 凭据校验和路由约束防止误接入及错误分发；全权限 worker 可运行 shell，不能据此承诺恶意代码无法绕过。强隔离需额外限制进程可访问的凭据、文件和网络。
- 管理层记录全局并发预算，分配每仓库限额；实例执行时仍做本地容量检查。

第一阶段使用固定每仓库并发 1、限制同时运行的仓库数量，避免先实现复杂的跨实例调度系统。实例启动和恢复均计入容量，避免只限制新任务却让恢复任务超额。

## 7. 界面

插件入口包含“仓库”“群聊绑定”“任务”“设置”。底层 Trigger / Eval 等详情仍可进入，但不作为新手首页。

仓库页面：添加已有本地仓库、识别远端、验证账号权限、选择工作模式、启动实例。显示连接状态、队列、当前任务和打开工作空间入口。

群聊绑定页面：选择机器人已加入的群、选择仓库、设置允许发起任务的人、连接检查、保存。复用现有群选择能力，不要求输入 chatId。

统一任务页面：按仓库过滤，展示需要回答的问题、运行状态和验收结果。回答、停止与重试都带 repositoryId，进入实例现有接口。

配置流程：环境检查 → 添加仓库 → 连接机器人 → 选择群 → 设置权限 → 本地自检 → 明确发起试单。

自检不向群发消息、不推送代码；真实试单作为独立动作，由用户在绑定群 @机器人发起。保存成功只表示配置已保存，不能代替真实连通性结果。

## 9. 分阶段施工与退出标准

### 阶段 A：仓库执行基础

实现仓库路径校验、current 模式、目录复用与串行；保留旧工单路径。

验收：同仓库两工单不并发修改；会话绑定真实仓库；重试 / 重启回原会话；用户改动完整保留；准备失败残留目录不能被当成准备完成。

### 阶段 B：多实例管理

实现仓库注册、独立 profile / stateDir / 进程、实例间认证、健康状态与启动限额。先用测试投递接口验证两个实例，不接真实飞书事件。

验收：同机两个仓库分别执行；暂停、重启、配置错误不影响另一个；不会重复启动；聚合接口不存在 ID 冲突；令牌不进入浏览器。

### 阶段 C：单机器人多群分发

抽取集中消费，落地持久化队列、绑定与话题归属、受控回复和补读；复用实例 Engine 接单。

验收：A 群只到 A 仓库，B 群只到 B；重复消息仅一个工单；网络失败后不丢单；实例掉线后恢复原目标；消费者重启补收；回复只回原群原话题。

### 阶段 D：配置向导与统一面板

交付仓库添加、群选择、权限配置、连接检查、统一任务与结果入口，中英文覆盖，复用现有草稿 / 冲突处理机制。

验收：安装后的用户无需手写 shell / YAML 即可完成两仓库绑定；刷新不丢草稿；配置冲突可恢复；错误有明确修复入口；能从群中发起任务并从面板打开正确会话。

### 阶段 E：迁移与真实联调

从旧配置导入一个仓库和已有群。导入前备份，未确认前不改变既有接单进程。切换时暂停旧消费者、记录接入水位并补收，再启用集中消费者；允许重投，以幂等消重。

验收：原有开放工单、话题归属、会话、待发回复仍可续接；新旧消费者不同时工作；回退可重放切换期间的入站记录。不能只恢复旧数据库而丢弃新入口已确认的消息。回退步骤在灰度前演练。

## 10. 核心验证矩阵

- 路由：一仓多群、一群拒绝重复绑定、群改名、路径别名、仓库远端不匹配。
- 权限：未授权发送者、未绑定群、私聊、伪造目标仓库、回复目标越界。
- 可靠性：重复事件、投递后确认丢失、机器人断线、实例离线、双方重启、待发回复恢复。
- 变更：绑定停用、群换绑、旧话题追问、旧工单恢复、仓库归档、凭据轮换。
- 执行：后台工作占位、串行、公平性、用户修改、分支冲突、准备失败残留。
- 界面：群列表不可读、机器人不在群、权限不足、实例未启动、保存修订冲突。
- 回归：现有 pnpm check 全量通过；新增边界采用真实临时 Git 仓库与可控接入替身测试。
- 实际联调：使用两个测试仓库、两个测试群，由明确允许的账号发起无破坏的小任务，确认接单、追问、修改与结果全链路。

自动化测试通过不替代实际 DSH 工作空间与飞书接单验证。最终交付附两仓库运行截图、路由记录及可审阅的结果。

## 11. 交付节奏

按 A → B → C → D → E 拆为可独立审阅的变更。每个阶段通过退出标准后再推进下一阶段。

首次可用闭环以“两个仓库、两个群、一个机器人，消息不串仓、会话有正确目录、重启不丢单”为准。自动 worktree、跨仓库任务和更强权限隔离在这个闭环稳定后单独排期。
