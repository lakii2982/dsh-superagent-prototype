# SuperAgent 改造方案：在一个 Desktop 内运行多个仓库

**版本**　V1.0 · 2026-11-24 · 设计稿，供开发与验收使用

## 一、交付后怎么用

管理员在 DeepSeek Harness Desktop 设置一次模型提供方和默认模型，从侧栏进入 SuperAgent，添加仓库、选择本地目录、绑定机器人和飞书群。之后，在群里给指定机器人发任务，Desktop 自动找到目标仓库，创建工单，通过 Desktop 的模型服务执行。点击工单中的“打开会话”，应当在当前 Desktop 窗口直接打开这张工单的会话。

例如，产品群和研发群可以共用同一个机器人。产品群绑定 ai-workspace，研发群绑定另一仓库。两个群同时发任务时，两张工单可以并行使用 Desktop 的模型，各自在自己的工作目录修改文件，回复回到各自的原话题。管理员只需要关心“哪个仓库在做什么”，无需记住后台端口、切换 profile 或为仓库重复登录模型账号。

**本期交付范围**是本机 Desktop 多仓库模式。建议沿用现有仓库管理、飞书接入和单仓库工单引擎，为 Desktop 增加进程内的仓库执行方式。已有独立服务器部署继续走原有启动和运维流程，便于企业在另一台机器上独立部署。这里的“一套 Desktop”指只有一个 DSH 宿主和 profile。Git、飞书 CLI、用户明确配置的外部编码工具仍可由宿主按需启动。Desktop 完全退出或电脑休眠期间，桌面工作流也会暂停。

## 二、为什么不能只改端口或隐藏插件

| 当前代码或数据 | 已确认的行为 | 对改造的影响 |
|---|---|---|
| src/index.ts | Desktop 多仓库开关走 Manager 分支，单仓库分支才直接创建 Runtime | 入口和开关可以沿用，需要让 Manager 能管理本机 Runtime |
| src/manager/instances.ts | 创建仓库专属 DSH_HOME，从 web 模板生成 profile，安装插件，再启动独立 dsh 进程 | 新 Desktop 仓库跳过整条创建进程的路径；隐藏入口无法复用模型 |
| src/manager/runtime.ts、store.ts | 仓库登记会分配端口，健康、投递、页面代理、停止和打开工作空间都依赖实例；停止会按 PID 发信号 | 启停、健康和导航必须一起改。尤其不能把 Desktop 的 PID 当成可停止的仓库实例 |
| src/app/runtime.ts、http.ts | Runtime 占用自己的数据库锁，同时注册统一的 /orchestrator 路由 | 保留每仓库一份存储；同一个 Desktop 上由管理器统一注册外部路由 |
| src/app/sessions.ts、executor/dsh.ts、sources/github.ts、sources/feishu.ts | 会话和执行器监听宿主事件，来源插件通过 orchestrator 服务寻找运行时 | 加入仓库所有权检查，并调整来源注册，否则会串会话或重复监听 |
| src/app/role-models.ts | 支持按角色指定模型；创建会话时通过当前宿主解析配置，并保护已有会话的模型选择 | 可以复用现有模型逻辑。先验证“默认继承”与“显式选择”两条路径 |
| src/client/manager.tsx、navigation.ts | 管理入口已有按仓库展示页面的能力，目前受管仓库的会话按钮可转到独立工作空间 | 保留熟悉的工作台，按钮改为定位当前 Desktop 内的具体会话 |

本机登记了 lakii2982/ai-workspace（51486）和 lakii2982/dsh-superagent-prototype（57796）。端口是旧实例登记值，登记本身不能证明服务正在运行。此次只读检查中，ai-workspace 有 2 张工单，均已结束。Desktop 默认提供方为 opencode-go，默认模型为 deepseek-v4.1-flash。另一个仓库的工单、两个仓库的积压消息、未发送回执和未提交文件，都须在真正切换时重新盘点。

## 三、目标架构与数据归属

| 对象 | 归谁管理 | 落地方式 |
|---|---|---|
| 模型提供方、登录凭据、Desktop 默认模型 | Desktop | 各仓库使用宿主的模型与会话服务。仓库设置只存可选的模型选择，不复制凭据 |
| 仓库列表、团队信息、机器人、群绑定、入站队列 | SuperAgent 管理器 | 复用 manager.sqlite 和现有绑定规则；管理器负责确定每条消息的唯一目标 |
| 来源授权、工单、执行策略、提示词、回执、重试状态 | 对应仓库 | 继续使用原 repositoryId 和 repositories/<id>/orchestrator.sqlite，避免迁移时重编工单号 |
| 新建的 DSH 会话、工作空间及模型选择 | Desktop 持久化；仓库登记归属 | 保存 repositoryId、工单或角色、sessionId、workspaceId 的关联；历史会话采用单独的来源映射 |
| Git 工作副本 | 对应仓库和工单 | 复用现有 worktree 创建、占用和回收逻辑。仓库根目录选择与 Git 远端校验继续生效 |
| 飞书身份和对外回复 | 原机器人、原群和原话题 | 凭据由机器人连接持有。任务只获得本仓库被授权的操作，复用原回执标识 |
| 外部编码 CLI | 该工具自己的授权与运行环境 | Desktop 中的 SuperAgent 模型调用走 Desktop 提供方。若工单委派给独立 Codex 或 Claude CLI，界面单列工具身份和失败原因，不承诺这些工具消费 Desktop 的模型账号 |

**执行链路。** 管理器先把事件和目标仓库落库，再交给对应仓库的运行时。仓库确认已持久化后，管理器才标记投递成功。运行时完成工单后，沿原绑定回复。即使两端改成同一进程，仍保留这两个持久化步骤。这样 Desktop 在中间退出，重启后可以重投，同一个事件仍只生成一张工单。

**适用边界。** 同一个 Desktop 账号内的仓库共享宿主、模型额度和操作系统身份。每仓库数据库、工作目录和权限检查提供工作流隔离。若交付合同要求不同客户拥有独立进程、系统账号或故障域，应使用独立部署。Desktop 自身崩溃会影响其中所有仓库，重启恢复是本期验收项。

## 四、六个施工包

### P0　先证明同一 Desktop 能承载两个仓库

在临时数据目录用两个测试仓库、同一测试 Desktop 宿主创建两组主会话和工单会话。刻意使用相同工单标题和相同外部事件编号，再打开一个普通 Desktop 聊天。记录各会话收到的工具、提示词、任务事件、工作目录和实际模型选择。对照 Desktop 的模型默认值测试一次真实的轻量请求，并单独验证历史会话可读路径。

**通过条件**：两组仓库均能返回结果，普通聊天收不到 SuperAgent 工具或通知，停止测试仓库 A 后 B 和 Desktop 聊天仍能工作。先验证 Cordis 服务作用域、事件订阅清理和 DSH 历史读取能力。若宿主无法可靠隔离同名服务，采用“单个宿主服务按会话归属分发”的实现，重新执行本步骤。

### P1　把仓库管理和进程管理拆开

在 src/manager/runtime.ts 中梳理所有仓库操作，覆盖启动、停止、健康、工单查询、暂停、接单、页面 API、打开会话和回收。沿用 ManagerStore 与现有 API 对外语义，为这些操作分别接入 Desktop 进程内运行时和现有独立实例。旧部署继续由 instances.ts 负责；Desktop 的停止操作只释放指定仓库的资源。让仓库标识成为必需字段，端口、profile 和进程号只对独立实例有意义。读取旧登记时保留这些字段，用于迁移和回退。

启动采用按仓库互斥和容量预留。重复点击启动复用同一次启动结果；初始化失败释放锁、订阅和容量。区分已登记、启动中、运行中、暂停调度、停止中、已停止、故障。暂停调度的仓库继续记录已授权输入，运行中的任务按既有语义处理。保存启用意图，Desktop 重启时只恢复应启用的仓库。

**通过条件**：启动两个测试仓库都不分配仓库监听端口、不生成 profile、不执行 dsh plugin add。旧的独立部署仍能启动、查询和停止。连续两次启停同一仓库，端口数、监听器数和数据库锁回到预期状态。

### P2　让多个运行时安全共享宿主

保留每仓库一份 Engine、Store、效果队列、执行器和状态目录。拆分 Runtime 中的“运行仓库”和“向宿主注册公共服务”。管理器统一注册 HTTP 路由，前端仍按 repositoryId 请求。直接调用经过授权的仓库操作，沿用原请求校验、操作权限、错误映射及数据范围。避免为了本机调用而跳过企业试点授权。源码中以 machine.managed 或企业试点标志判断的地方逐项复核，明确是“仓库受管理”还是“需要跨进程传输”。

集中管理会话归属。新会话标识包含稳定的仓库身份，可使用已有 DSH ID 规则允许的编码。已有工单 ID、外部事件 ID 继续有效。覆盖主会话、工单会话、子代理、重试消息及历史链接。工具注册、提示词、回执、取消、恢复和订阅都按可信的会话归属定位仓库。宿主事件缺失归属时跳过，并留下可诊断信息。普通 Desktop 会话完全沿用宿主配置。

GitHub 按仓库启动来源，飞书按机器人维持连接。仓库可通过受约束的内部调用请求机器人操作，复用现有机器人、群、仓库和接单人核验。处理重复事件、群换绑、断线补收、回复发送后本地尚未记账等情形时，沿用稳定标识和原有重试约定。停仓库时先停止领取新工作，等待在途写入结束，再清理本仓库的监听、定时器和锁；管理器保留其他仓库及机器人的连接。

**通过条件**：用 A 的会话访问 B 的工单、发送 B 的回复或调用 B 的写工具，均被拒绝；相同外部事件在同一绑定内重放只产生一张工单。A 的来源异常或任务异常后，B 仍能接单和交付。

### P3　复用 Desktop 模型并能核对实际调用

新仓库的评估与执行模型默认选择“继承 Desktop”。显式设置角色模型时，通过 Desktop 的提供方解析和验证该模型。已有会话保留已经记录的模型选择。用户修改全局默认后，新建且未设角色覆盖的会话采用新默认；验证已有会话下一次调用的实际行为，界面按宿主返回值展示。执行失败时显示仓库、会话、实际提供方、模型和可操作的错误原因，禁止静默切到另一收费账号。

界面至少区分“配置来源”和“本次实际使用”。例如前者是“继承 Desktop”，后者是“opencode-go / deepseek-v4.1-flash”。授权失败、模型不存在或提供方限流时，保留工单和可重试状态。多仓库共享同一个账号额度，沿用每仓库并发设置，再由 Desktop 管理器限制总活跃任务数，优先采用轮流取单，避免一个仓库耗尽全部名额。外部 CLI 的可用性单独检查。

**通过条件**：在两个仓库各创建新工单，实际 DSH 请求元数据均命中当前 Desktop 提供方；修改一个仓库的角色模型只影响适用的新会话。测试过程中变更模型使用临时环境。交付证据只记录提供方、模型、会话及请求结果，不输出密钥。

### P4　统一 Desktop 操作入口

侧栏只保留一个 SuperAgent。仓库列表显示仓库、运行状态、排队数和最近错误。仓库详情在当前窗口内展示来源、工单、执行设置和模型来源。将“打开仓库工作空间”的笼统跳转改成工单上的“打开会话”，经会话目录核对后打开准确的 sessionId。历史只读会话显示“查看历史会话”。管理员无需看到本机端口、profile 或桥接凭据。

仓库故障显示在对应仓库行。暂停、停止、全局退出用不同文案说明后果。用户点击停止时如有执行中的任务，提供“完成当前任务后停止”，显式中止走已有的任务中止流程。桌面退出后再次进入，应当恢复仓库列表、绑定、排队任务和可继续的会话。

**通过条件**：从 Desktop 完成“配置提供方 → 加两个仓库 → 绑定群 → 接单 → 看工单 → 打开具体会话”全流程，整个过程无需打开仓库端口页面。一个仓库停止后，另一个仓库的工作台和普通桌面会话可继续使用。

### P5　迁移已有安装并演练回退

按仓库逐个迁移。建议先用临时仓库走完整流程，再迁 ai-workspace，最后迁另一个仓库。每个仓库记录旧部署方式、目标方式、迁移阶段和核对结果。旧进程仍拥有仓库写锁时，不启动新的运行时；重启迁移工具应能从记录的阶段继续。

| 步骤 | 执行动作 | 进入下一步的依据 |
|---|---|---|
| 1. 盘点 | 列出仓库 ID、工单开闭状态、活跃任务、待投递事件和回执、模型覆盖、主/工作会话、工作树和未提交改动 | 生成按仓库的迁移清单。关闭的工单也要核对会话是否可定位 |
| 2. 排空 | 暂停目标仓库领取新任务，入口继续持久化新消息。等待已启动任务及外部写操作结束，记录最后处理位置 | 目标仓库无在途外部操作，旧消费者和可恢复队列的边界清楚 |
| 3. 停写与备份 | 停止并核验旧实例身份及锁释放。用 SQLite 一致性备份保存管理库和仓库库，保留旧会话目录、工作空间索引与未提交工作树 | 在临时目录打开备份，抽查工单、会话和回执。其他仓库运行时管理库备份只作参照 |
| 4. 接入历史 | 沿用仓库库和工单 ID；建立旧会话来源映射。优先用宿主支持的读取或导入方式。在兼容性未验证前提供只读历史查看，支持定位消息、结果和关联工单 | 历史工单可从 Desktop 打开对应记录；明确标注可续跑或仅可查阅。开放工单需验证上下文可恢复，无法恢复则继续由旧运行方式处理至结束 |
| 5. 先验后写 | 新运行时在不领取任务、不发送回复的状态下检查目录、模型、权限和会话。核对清单后，将该仓库执行归属切至 Desktop，再消费积压 | 新旧消费者互斥；旧服务停止后 Desktop 仍能处理新工单 |
| 6. 验证 | 通过预先指定的试单验证一次完整往返，核对队列、回复、工作树、实际模型和会话归属。保留原数据和迁移日志 | 每个旧工单有对应记录，积压可解释，同一消息只有一次业务效果 |

**回退规则**：新运行时还未开始写入时，释放其仓库锁并恢复旧实例即可。已接单、创建新会话或发出回复后，先暂停并盘点增量，再按映射接续；新会话无法在旧实例续跑时，先完成或显式交接该工单。保留投递和外部操作回执，避免重复开 PR、重复发消息。禁止用旧的全局数据库快照覆盖其他仓库在此期间的新数据。单仓库回退演练通过后，再扩大迁移范围。

## 六、实施顺序与发布决策

**第一批**完成 P0、P1，交付双仓库原型和原模式回归结果。**第二批**完成 P2、P3，交付双仓库并行执行、真实模型调用和重启恢复证据。**第三批**完成 P4、P5，在真实 Desktop 上验收入口、会话导航、历史记录和单仓库回退。单元测试优先覆盖现有 manager、runtime、sessions、HTTP、面板和工作树套件，再运行仓库已有 pnpm check；进程数量、实际模型、原生窗口导航及历史兼容性需用真实宿主验收。

开发默认采用三个决定：新建 Desktop 多仓库工作区使用进程内执行；现有安装按仓库迁移；完成的历史会话优先保证在 Desktop 可查阅，对仍需续作的会话另做恢复核验。真实宿主双仓库、现有工单迁移和回退三项都通过后，再把新方式设为现有用户的推荐升级路径。实施期间以验收矩阵与证据为交付依据。
