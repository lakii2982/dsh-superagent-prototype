# DSH 企业研发试点与验收

公司目标覆盖 5 个开发团队、120 名开发者和 12 条产品线。开发者在现有 GitHub 或飞书入口提交迭代，DSH 完成隔离工作目录内的实现和检查，交付草稿 PR。代码负责人评审、合并，沿用产品线的发布流程。**每条产品线的验收目标是从需求就绪到生产发布的中位周期缩短至少 50%。**

## 试点交付范围

| 使用人 | 日常动作 | 交付与证据 |
| --- | --- | --- |
| 需求人或开发者 | 用已授权身份在 GitHub 议题或已绑定飞书群 @ Agent，写清工单号、目标、验收条件和已知边界 | 工单进入该仓库。追问在原话题进行 |
| DSH 执行器 | 每单使用独立 worktree，先复现业务现象或验证现状，再实现并运行检查 | 草稿 PR 包含工单链接、改动摘要、实际检查结果和待人工验证项 |
| 代码负责人 | 依据 PR 差异和当前提交的 CI 结果独立评审，再合并 | GitHub 评审、合并与 CI 记录关联同一工单 |
| 发布负责人 | 按现有发布流程确认变更已进入生产并回填时间 | 可从工单追溯到包含该变更的生产版本 |
| 运维人员 | 管理授权名单、队列、实例、故障和审计证据 | 只有运维身份进入本地管理面板，开发者继续使用原渠道 |

首轮选可描述验收条件的局部缺陷、回归测试、文档修正和小型兼容功能。权限、机密、CI 改造、生产基础设施、发布配置和数据库迁移留在原审批流程。可在 GitHub 和飞书复用同一条发单格式：`工单 DEV-123｜修复行为……｜预期结果……｜验证步骤……｜改动边界……`。

## 统一 DSH 管理服务的部署配置

全公司只部署一个 DSH 管理服务。管理页面按团队筛选，同时保留仓库、投递队列和产品线的全局视图。每个仓库有独立 DSH 工作目录、会话、GitHub 执行账号和接单名单。一个代码库可服务多条产品线，一条产品线也可以跨多个代码库。公司发布台账用稳定工单号与产品线关联，跨仓工单计一次。

在受控专用 VM 内运行管理器及其子实例，并为这套服务分配专用 OS 身份。子实例的目录与会话独立，当前运行边界是整台 VM，适用于纳入同一信任域的五个团队。仓库不得持有生产发布凭据。开发者用现有 GitHub 或飞书身份接入。受控运维工作站通过本地访问或 SSH 转发使用统一页面。

| 配置 | 初始值与操作 |
| --- | --- |
| DSH Web profile | 使用 [企业上线包](../ops/enterprise/README.md) 创建统一管理 profile，集中导入团队、产品线、仓库和人员权限。旧 profile 和数据目录独立保留 |
| 仓库名额 | 上线包默认分配 12 个仓库名额。每个新仓库初始同时执行 1 单。按队列等待和宿主负载调整 |
| GitHub | 在 `github.com` 为各仓库配置专用执行账号和最小范围的凭据。先配置目标分支必须经 PR、人工审批、指定 CI 检查，新提交使旧审批失效。Agent 身份不得绕过规则或执行受保护分支的合并。用不同身份实际验证，并测算多个仓库轮询的 API 额度 |
| 飞书 | 可选。统一管理器使用一个专用机器人，只加入已授权的研发群。每个群绑定唯一的目标仓库。先校对群号与人员名单，再开放接单 |
| 模型与宿主 | 在试点实例配置公司批准的模型和额度。运行身份只持有分配给它的工作区及经审批的凭据，宿主网络与生产权限由部署环境约束 |
| 运维访问 | 管理面板绑定 `127.0.0.1`，由持运维凭据的操作者访问。开发者的接单身份由 GitHub 和飞书名单控制 |

GitHub 分支规则的设置与验证参见 [GitHub Rulesets 官方文档](https://docs.github.com/en/repositories/configuring-branches-and-merges-in-your-repository/managing-rulesets/available-rules-for-rulesets)。GitHub 账号和飞书机器人配置步骤见 [部署手册](006-deployment.md) 与 [多仓库运行说明](multi-repository.md)。

在有 DSH、Node、pnpm 的试点机器上，从此项目目录执行：

```bash
pnpm install --frozen-lockfile
pnpm check
dsh enterprise-pilot --from-default-profile web --dump-config >/dev/null
dsh plugin --profile enterprise-pilot add "link:$PWD"
```

将示例复制为该新 profile 的 `cordis.patch.yml`，修改状态目录和端口，然后运行 `dsh --profile enterprise-pilot --no-open`。启动后通过面板登记与验证 GitHub 仓库及允许的开发者。需要飞书时连接机器人、刷新群列表并绑定。使用新配置和新状态目录先跑两仓联调，现存管理器和仓库实例的工单迁移按原部署手册处理。

每个仓库启动后，点击「打开仓库工作空间」，在该仓库的 DSH profile 中配置公司批准的模型和凭据，再发一张低风险试单验证模型请求。试点实例使用自己的 `DSH_HOME` 和凭据文件，管理器的模型登录不会带入实例。实例就绪与 GitHub 连接通过后，仍需要实际模型调用才能完成这一项验收。

## 验收顺序

| 门槛 | 验收动作 | 通过依据 |
| --- | --- | --- |
| 本地候选 | 执行仓库检查，验证容量、队列、授权、工作目录和草稿交付 | 保留测试与构建输出。合成数据证明对应程序行为 |
| 真实联调 | 1 个团队、2 条产品线，从真实 GitHub 或飞书分别发单。故障期间保持另一仓库运行，恢复后对账。分别用授权和未授权账户发起新单和追问 | 原话题、工单、草稿 PR、人工评审与测试能逐项对应。未授权输入不创建、推动或恢复任务。重试和重启后没有重复投递或草稿 PR |
| 容量放行 | 分批接入 2、6、12 条产品线。复核 5 个团队的账号和仓库正反向映射。使用实际拓扑测量 120 个身份的入站波次，持续运行一轮团队高峰 | 对账应收与实收、唯一工单、队列等待、人员越权、CPU/内存、模型预算和外部服务限流。故障演练、访问边界和停用回退均有记录 |
| 业务成效 | 各产品线独立计算需求就绪到生产发布 P50 和 P90，检查发布完成比例与回滚 | 每条线达到 50% 目标且 P90、发布完成比例与回滚情况满足验收，方可宣告整体达成 |

本地验收已通过类型检查、构建和 1,310 项无需监听端口的测试。管理器另有 11 项集成测试在进程内传输替身中通过。DSH 0.2.2-rc.5 已以同样方式加载编译后的管理器和仓库实例，并核对试点模式和接口鉴权。本地环境禁止监听回环端口，另有 8 项服务脚本测试需在允许端口监听的环境补跑。

容量演示可运行 `pnpm exec vitest run tests/manager-bootstrap.spec.ts tests/manager-capacity.spec.ts`。其中合成场景使用 5 个团队、12 个模拟仓库实例和 120 个不同身份，断言持久投递、去重、重启重新发现、第 13 个实例受限以及离线积压不阻断其他仓库。真实 GitHub、飞书、模型和生产发布仍由上表的联调与业务验收覆盖。

急需撤权时先暂停调度并停止受影响的仓库实例，再更新名单。重启后保持暂停，确认名单同步，再恢复调度。飞书试点暂停时同步停用相关群绑定。恢复前用工单、远端分支、PR 与原话题对账，保留管理数据库、仓库数据库、会话和 worktree 以及停用前接收的事件。切换同一机器人事件流时先停止旧消费者，再启动新消费者。

## 50% 怎么算

以每条产品线的普通迭代为样本，统一记录需求就绪、开始实现、草稿 PR、合并和首次包含该变更的生产发布时间。完整周期从**需求符合开工条件**开始，到**首次进入生产**结束。以四周为基准周期，比较接入前连续四周和稳定运行后连续四周进入 Ready 的同类工单。两个观察窗的起止口径、工作类型和跟踪上限一致。保留未发布项，同一工单跨仓变更只计一次。

使用 [测量脚本](../scripts/enterprise-measure.mjs) 输出各线的样本、时长和验收结论。先运行合成示例确认格式，然后使用发布台账导出文件。每线基准与试点各至少 20 项。样本不足或无法观察 P90 的产品线继续收集证据。质量负责人用生产回滚或变更故障记录补验交付质量。

```bash
node scripts/enterprise-measure.mjs examples/enterprise-measure.example.json
```

导出包含 `baseline`、`current` 两个 Ready 窗口，`asOf` 表示数据截点，`followUpDays` 设定各工单的固定跟踪期，示例采用 28 天。`products` 列出 12 条产品线及 5 个团队的归属。每条 `workItems` 包含 `id`、`productId`、`workClass`、`readyAt`、`releasedAt`，未发布填 `null`。两个窗口按同一个 `eligibleClass` 取样。等试点窗口结束且最后一批工单完成等长跟踪后，脚本才出比较结果。退出码 `0` 表示 12 条线全部达标，`2` 表示至少有一条线未达标，`3` 表示证据不足，`1` 表示输入有误。

每周查看四段用时：就绪到开工、开工到草稿 PR、草稿 PR 到合并、合并到上线。先处理该产品线最长的一段。若等待评审和发布占了多数，压缩写代码时间以后仍需处理评审排队和上线批次，才能达到总周期目标。

## 上线依赖与负责人

| 依赖 | 公司负责人 | 验证证据 |
| --- | --- | --- |
| 12 条产品线与实际仓库、发布记录的映射 | 研发负责人和产品线负责人 | 产品线 ID、团队 ID、仓库、负责人、发布系统工单字段 |
| 120 名经授权的开发者范围 | 各开发团队负责人 | 名单与 GitHub / 飞书身份对照，入组和撤权验证 |
| 运行主机、专用账号、模型和网络配额 | 企业 IT、研发效能或安全负责人 | 一台专用主机、模型和额度、分支规则与 CI 验证结果 |
| 周期基线、质量与回滚数据 | 发布负责人或研发效能负责人 | 同口径历史导出、生产发布时间、回滚记录 |
