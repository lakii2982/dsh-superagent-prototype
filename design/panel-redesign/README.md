## 0. 最终整合方案

[`solution.html`](solution.html)：V1 的三栏队列分栏与 `⌘K` 命令面板，加上 V3 的设置页与视觉语言。

- **导航**：64px 图标栏，当前项黑色圆角块；仓库上下文回到队列顶部，避免再占一列。
- **队列**：340px，保留 V1 的「需要你 / 进行中 / 最近结束」与筛选；选中项浅灰底 + 左侧黑线。
- **详情**：V3 的标题层级、16px 问题卡、细线时间线与克制留白；回复、重试、执行信息在同一侧完成。
- **设置**：隐藏队列、占满内容区；V3 的四步首次配置、来源 / 仓库 / 准入 / 执行 / 部署卡片与底部保存条。
- **命令面板**：V1 的分组与键盘操作，V3 的圆角、半透明底与轻阴影。
- **视觉**：黑主按钮、系统字体、12/13/14/16/20 字号、16px 卡片、1px 发丝线；蓝色只做链接与进行中，紫色只做完成。

整合后仍然保留四个入口：今日 / 工单 / 流水 / 设置；来源、触发、评估合并进「流水」的筛选与详情。

## 1. 现状与问题

现有面板（`docs/005-panel.md`）按 Overview / Source / Trigger / Eval / Execution / Settings 六个页签组织。信息架构完整，但打开后的第一眼不够聚焦：

1. **首屏是同权重的四块**：待处理工单、系统问题、24 小时流水、执行器负载并排出现，用户要自己判断先看哪一块。
2. **一条工作被切成三页**：来源在 Source、消息与判断在 Trigger、决定在 Eval、工单在 Execution；追溯一次追问要跨页跳转。
3. **操作与上下文分离**：追问、重试、恢复等动作分散在列表行和详情里，处理时必须离开当前列表。
4. **配置与运行混在一起**：设置里的表单和运行监控共用一套视觉层级，首次配置的引导感弱。

这次不改领域模型，只回答三个问题：

- 打开面板 3 秒内，能否知道**现在需要我做什么**？
- 一件事从触发到结果，能否在**一条连续路径**里读完并处理？
- 系统健康时能否**安静**，只在需要人时占用注意力？

## 2. 设计基线（DeepSeek Harness 设计规范）

原型直接采用 DSH 的语义令牌（`--dsw-alias-*`），值取自当前 light palette；组件命名与间距遵循面板现有实现，便于后续移植回 `src/client`。

| 类别 | 令牌 / 规则 | 用途 |
| --- | --- | --- |
| 画布 | `--dsw-alias-bg-base` `#fff`；`--dsw-alias-bg-module-platform` `rgb(245 246 247)` | 主区纯白，导航/侧栏用极浅灰 |
| 文字 | `label-primary` `rgb(15 17 21)`；`label-secondary` `rgb(97 102 107)`；`label-tertiary` `rgb(129 133 140)`；`label-caption` `rgb(173 178 184)` | 标题 / 正文 / 辅助 / 说明 |
| 边框 | `border-l2` `rgba(0,0,0,.10)`；`l3` `.12`；`l4` `.16` | 1px 发丝线，不用重描边 |
| 交互 | `interactive-bg-hover` `rgba(38,49,72,.06)`；`active` `.10` | 行、按钮、菜单的 hover / 选中 |
| 主操作 | `brand-primary` `#0f0f0f` | 黑色主按钮；一屏最多一个 |
| 业务色 | `state-business-primary` `#4176e6` | 链接、进行中、可交互提示 |
| 状态 | 成功 `#22c55e`；等待 `#f59e0b`；错误 `#ec1313`；完成 `#7c3aed` | 只表达状态，不做装饰 |
| 圆角 | 8 / 12 / 16 px | 控件 / 卡片 / 大面板 |
| 字体 | 系统字体栈；正文 14/22，辅助 13/20，说明 12/18；标题 16/24、20/28 | 与 DSH Web 一致 |
| 动效 | 200ms `cubic-bezier(.4,0,.2,1)`；`prefers-reduced-motion` 关闭 | 只用于状态切换与浮层 |

**使用纪律**

- 蓝色只用于链接、进行中、业务提示；不用蓝色大面积铺底。
- 紫色只表示「已完成 / 已合并」，不表示可点击。
- 不用渐变、玻璃拟态、彩色图标底；阴影只用于抽屉、菜单、命令面板。
- 数字必须能在对应列表里找到等长内容；空状态明确说「没有需要你处理的事」。
- 圆角与发丝线优先于阴影；界面安静，问题才占用空间。

## 3. 方向探索（过程稿）

三版使用**同一份模拟数据**（2 件需要你、1 个连接问题、2 个执行中、3 条近期结束），差异在信息组织与主交互。最终方案取 V1 的骨架与 V3 的细节。

| | V1 队列分栏 | V2 流水看板 | V3 简报工作台 |
| --- | --- | --- | --- |
| 一句话 | 左侧导航 + 中栏队列 + 右侧详情，像处理收件箱 | 按生命周期分栏，卡片点开抽屉，像看板 | 单栏简报 + 右侧检查器，像读一份每日工作简报 |
| 打开后先看到 | 需要你处理的队列 | 工作在全流程中的位置 | 一段解释「今天发生了什么」的文字 |
| 主交互 | `j/k` 移动、`Enter` 打开、`⌘K` 命令面板、行内操作 | 点卡片 → 右侧抽屉；顶部筛选实时过滤 | 展开卡片 → 右侧检查器；专注模式隐藏导航 |
| 适合 | 每天多次处理、追求速度 | 同时看多条工作、关注堵点 | 低频监督、先读上下文再处理 |
| 主要取舍 | 窄屏下详情空间紧张 | 卡片会截断上下文 | 一屏信息量最少，批量处理慢 |

### V1 · 队列分栏（Focus Queue）

```
┌──────────┬──────────────────┬─────────────────────────────┐
│ 今日  2  │ 需要你  2        │ 修复飞书追问在重启后丢失上下文 │
│ 工单  4  │ ▸ 等待回复  12m  │ 等待你回复 · 飞书 · 林舟     │
│ 流水     │ ▸ 验证失败  38m  │ ─────────────────────────── │
│ 设置     │ 进行中  2        │ 问题 / 发生了什么 / 时间线     │
│          │ ▸ 设计规范… 32m  │ [回复] [打开工单]             │
└──────────┴──────────────────┴─────────────────────────────┘
```

- 三段固定：196px 导航、360px 队列、剩余详情；队列与详情都独立滚动。
- 默认选中第一件「需要你」的工作，右侧直接给出问题和回复框，不用再点一次。
- `j/k` 在队列移动，`Enter` 打开详情，`⌘K` 打开命令面板（跳转、搜索工单、执行动作）。
- 行内提供最常用的一个动作（回复 / 重试 / 查看），其余收进详情。

### V2 · 流水看板（Flow Board）

```
┌────────────────────────────────────────────────────────────┐
│ Superagent  dsh-superagent-prototype  feat/...  [搜索] [我] │
│ 今日 18 收到 · 6 过滤 · 12 判断 · 3 接单  执行器 2/3  ● 飞书 │
├──────────┬──────────┬──────────┬───────────────────────────┤
│ 新触发 1 │ 等待你 2 │ 执行中 2 │ 已结束 3                  │
│ ┌──────┐ │ ┌──────┐ │ ┌──────┐ │ ┌──────┐                  │
│ │消息… │ │ │追问… │ │ │设计… │ │ │#58   │                  │
│ └──────┘ │ └──────┘ │ └──────┘ │ └──────┘                  │
│          │          │          │          打开 → 右侧抽屉  │
└──────────┴──────────┴──────────┴───────────────────────────┘
```

- 顶部一条状态带回答「今天流进来多少、卡在哪、执行器是否健康」。
- 四列对应真实生命周期：新触发（待判断）→ 等待你 → 执行中 → 已结束；「等待你」列固定第二列，保证最先被看到。
- 点任意卡片从右侧滑出抽屉（440px），保留看板位置；抽屉内完成回复、重试、打开会话、查看 PR。
- 顶部搜索即时过滤卡片；筛选 chip 只影响当前列，不改变数据口径。

### V3 · 简报工作台（Briefing Desk）

```
┌────┬──────────────────────────────────────────────┐
│icon│  11 月 17 日 · 星期一        专注模式  [搜索] │
│ 今 │  ┌────────────────────────────────────────┐  │
│ 工 │  │ 今天有 2 件事需要你                     │  │
│ 流 │  │ 修复飞书追问…  等待回复 12m  [回复]     │  │
│ 设 │  │ 为 Manager 增加健康检查  失败 38m [重试]│  │
│    │  └────────────────────────────────────────┘  │
│    │  系统：飞书连接中断 15:42 → 检查设置          │
│    │  正在发生  2 条 · 刚刚结束  3 条（可展开）    │
└────┴──────────────────────────────────────────────┘
```

- 64px 图标导航 + 840px 阅读栏；首页是一份「今日简报」，先解释再给动作。
- 「需要你」用大卡承载问题原文与回复框，一次只处理一件事；系统问题压缩成一行。
- 点任意记录从右侧滑出检查器（420px）；「专注模式」隐藏导航和次要区块。
- 设置页把「首次配置」做成四步清单，配置完成后再显示高级项。

## 4. 三版共同覆盖

四类页面：

1. **今日**：需要你、系统问题、24 小时流水、执行器、正在发生、近期结果。
2. **工单**：列表 + 详情（来源、判断理由、会话、分支 / PR、时间线、追问回复）。
3. **流水**：触发 / 评估 / 丢弃消息，含过滤与原因。
4. **设置**：来源与账号、准入、执行、部署、首次配置清单。

共同覆盖的状态：

- 2 件「需要你」（一个等待回复、一个验证失败）
- 1 个「飞书连接中断」警告（可行动）
- 2 个执行中、1 个排队、3 个近期结束
- 全部使用 `assets/data.js` 的同一份数据

**与现有 Manager 页的关系**：本轮以 Superagent 主面板为主，但三版都把现有 Manager 页的仓库、群绑定和首次配置收进「设置」，作为同一套界面的一部分。如果评审认为 Manager 页本身才是重点，可以沿这三版的方向再单独展开一版管理台原型。

**本轮不覆盖**：暗色主题、移动端、真实 API、六个页签的一对一迁移。三版都把六个页签收敛为四个入口，这是需要评审确认的方向之一。

## 7. 证据与限制

- 所有内容为模拟数据；人物、工单号、PR 号均为虚构。
- 三版是交互原型，不是生产实现；未接入真实 API，未做暗色与移动端适配。
- 交互通过 URL 参数复现，便于评审和截图：
  - 整合方案：`?view=home|ticket|flow|settings`，`?palette=1` 打开命令面板，`?ticket=t-1042`
  - V1：`?view=home|ticket|flow|settings`，`?palette=1` 打开命令面板，`?ticket=t-1042`

  - V3：`?view=briefing|records|settings`，`?inspector=t-1042` 打开检查器
- 视觉基线截图来自当前插件构建的 Manager 页（同一设计语言）；主面板的实时截图因本地 GUI 需要启动凭证，未纳入本轮证据。
